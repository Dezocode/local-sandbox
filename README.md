# Local Sandbox

An iOS-style Oracle workspace with Shortcuts-based app providers, autosave, encrypted device sync, and reviewed repository connections.

Live private dashboard: https://local-sandbox.ctyy4wd4c2.chatgpt.site

## Start on your phone

Open the dashboard, then Apps & Shortcuts. Configure Locally, ChatGPT, Grok, Grokbot, or Claude using the named action your installed app exposes. Sign in inside that app. Local Sandbox does not use model API keys or model API billing. If an app offers no text-returning Shortcuts action, use the manual return flow.

The hosted app accepts either its ChatGPT host identity or a standalone Sign in with Apple session. A signed-in ChatGPT user can link Apple to the same workspace. Local Sandbox never matches or merges accounts by email. Link Apple in the web app before the first native sign-in if the native app must reopen an existing ChatGPT-owned workspace.

The native companion is in `ios/LocalSandbox.xcodeproj`. Choose your Apple Developer team and bundle ID, then build and sign. Native Sign in with Apple sends its nonce-bound identity token and strict one-use authorization code to the server. The server exchanges that code as the native client, retains the Apple refresh grant encrypted in D1, and returns a schema-v2 `pending` response with a 15-minute opaque Local Sandbox bearer. Before activation, the iPhone writes that exact response to the non-synchronizable, device-only `appleNativePendingActivation.v1` Keychain journal and verifies the readback. The journal also binds the target account-binding hash, activation purpose, and any transfer-recovery account-binding hash, so an ordinary, transfer-recovery, or deletion-reauthorization flow cannot consume another flow's record. The iPhone then checked-reads any prior active-bearer evidence and sends the pending bearer to `POST /api/auth/apple/native/activate` only when that evidence is readable and structurally valid. Only an `active` session can authorize `/api/sync` or `POST /api/auth/apple/native/refresh`. A pending session remains available only for activation or revocation and remains retention-bound. Apple refresh tokens never enter the device.

After a restart, the app can resume only an ordinary pending activation, and only after Apple reports the exact stored user as authorized and the person unlocks that local profile. Hosted admission remains blocked through activation and a fresh server refresh. Only then can the app restore hosted authority. Transfer recovery and deletion reauthorization require their explicit flows. The client samples time after each exchange, activation, or refresh response arrives. It keeps the server's exact expiry only when that value is still live and no more than 30 seconds beyond the 15-minute response window. Concurrent refresh responses for the same opaque bearer can only preserve the later valid expiry; they cannot replace the token or restore admission after a lock.

If an exchange creates a pending server session but the client can neither save its journal nor durably stage or remotely revoke the exact bearer, the client reports `APPLE_NATIVE_PENDING_SESSION_RECOVERY_LIMITED` and never admits the session. Pending sessions cannot sync or refresh. The server's grant-retention process then owns cleanup and keeps failed provider revocation available for another run. Source and local worker tests cover that retention path, but the deployed Cloudflare Cron Trigger and a real scheduled firing remain unqualified.

Explicit **Lock now** blocks hosted admission, then performs one serialized capture, batch stage, and checked handoff. It captures both pending and active native sessions, writes every still-revocable exact token to the bounded device-only revocation queue, verifies that batch, and only then clears matching active and pending Keychain records. A failed stage leaves the original evidence stored and blocked from use. A background transition or bearer expiry ends in-memory and admission authority but preserves the exact Keychain evidence needed for retirement.

The app retries saved revocations before it sends a new Apple authorization code to `/exchange`, after it promotes an active session, and when the person chooses the retry control in Settings. A confirmed revoke or authoritative HTTP 401 from `POST /api/auth/apple/native/revoke` removes only the matching debt; unrelated queue entries remain. The queue's `expiresAt` is a conservative server-grant horizon for status and retention reasoning. Device wall-clock time never clears the debt or makes its bearer admissible. Before authoritative account deletion completes, invalid pending-activation journal or revocation-queue bytes remain stored and block hosted admission instead of being treated as absent. After authoritative hosted deletion, checked cleanup may clear the matching pending-activation journal because the server has removed that account's session authority. Local files remain available when hosted access is unavailable.

A transferred-credential response and local-profile deletion both capture and durably stage every still-revocable session before clearing its bearer or scrubbing profile credentials. Profile deletion verifies the non-identity scrub before it deletes the stored Apple user as the final commit. A transferred credential disables hosted access until explicit Apple reauthorization proves old and new subject continuity and the app completes its journaled recovery, account-mode, Apple-user, and stable local-workspace binding migration. While a native Apple authorization ceremony is active, the UI disables a second ceremony and conflicting lock, profile, deletion-recovery, and revocation-retry controls.

Installing the native app registers its App Shortcuts automatically. Every intent that reads protected state, qualifies a provider, plans, or mutates declares `requiresLocalDeviceAuthentication`, so the executing iPhone must be unlocked even when another Apple device initiated the request. Open Local Sandbox alone remains `alwaysAllowed` and performs no data access. Siri and Shortcuts can choose Saved provider, Best local, Apple Intelligence, Locally, ChatGPT, Grok, Grokbot, or Claude for each task. Saved and explicit selections stay pinned and fail instead of substituting another provider. Best local considers only Apple Intelligence and Locally. Its cold start applies only while neither has comparable evidence: it targets Apple when that runtime is available, otherwise Locally, but blocks execution until that selected route has a current task-qualified suite. As soon as either local provider has comparable evidence, Best local uses the deterministic measured ranking and blocks if its selected route does not qualify. On iOS 27, Run Long Apple Task uses the system's long-running App Intent lifecycle for the direct Apple route. The iOS 26 Run, Begin, and Apply actions remain available. On an iPhone 18 Pro Max, the Apple route must qualify on device and in Airplane Mode. Lower or Apple-Intelligence-ineligible iPhones retain the same workspace and native App Shortcuts through explicitly selected provider actions that pass local qualification and live visual device acceptance.

For a provider app, compose Begin Oracle Task or Run Bounded Task → Get Dictionary from Input → Get `payload` → the user-reviewed provider Shortcut → Apply Validated Action. The setup recipe labels the supplied value as the provider action's raw JSON text to Apply, but Local Sandbox treats it as untrusted returned text and does not authenticate its source. Apply validates the proposed action against the saved resource, cloud, clipboard, path, hash, step, and failure boundaries; an unattended Siri flow does not display a separate per-action content-review screen. Decode Apply's returned envelope with Get Dictionary from Input, and repeat with its `payload` only while `phase` is `awaiting_response`. Otherwise retain or import the terminal receipt stored in `payload`. Run, Begin, and Apply return the same strict version 1 envelope with the resolved provider, requested selection, `on-device-apple` or `app-shortcut` decision, `phase`, output `kind`, `payload`, and the configured adapter name for a Shortcut route. The provider account and tokens stay in its app. The final device receipt identifies the resolved provider and Siri/App Shortcut origin and records each outbound and return hop by prompt/response SHA-256 plus a stable SHA-256 adapter fingerprint; it never exports the custom adapter name. Ordinary tool traces contain result kind, hashes, byte counts, readback kinds, and error codes instead of file, clipboard, or returned response text. The native app gates new work with its own qualification, run, pending-response, and applying-response states. After deliberate terminal-receipt import, the dashboard validates and displays the committed route plus ordered handoff hashes. It does not receive live native activity, provider authentication status, provider history, model activity, or cross-app telemetry.

## Deterministic provider qualification

The device-local qualification suite has five exact probes: `strict-json`, `read-tool`, `list-tool`, `patch-tool`, and `bounded-context`. The protected ledger stores at most 240 attempts. It admits at most one attempt for each provider, probe, and UTC day. Qualification scores use only the 20 freshest attempts from the last seven days. Evidence stays in the same epoch only while the device profile, full OS major, minor, and patch version, OS build descriptor, app version and build, provider, and adapter name and mode remain unchanged.

A base qualification needs all five completed probe types, a local schema-validation pass rate of at least 80%, an exact-assertion pass rate of at least 80%, and zero integrity faults. That means at least four schema-valid responses and four passing assertions in the first five-probe suite. Every task route, including direct Apple Intelligence, requires that full base qualification plus all three tool probes and enough tested context for that task. An external route used by Siri also requires an observed App Intent return for every probe. This observation means only that returned text reached Record Provider Check. It does not prove unattended end-to-end execution, the response source, the provider account, or the active model. Unattended acceptance requires live physical-device evidence. A manual-return route may be used only in a deliberate attended flow; it is never eligible for unattended Siri. The app ranks eligible providers by schema-validation rate and assertion pass rate. Equal external-provider scores then use lower observed App Intent round-trip time in 500 ms buckets. Apple records in-process model time, which is not compared with an external round trip. Remaining ties use this fixed order: Apple Intelligence, Locally, ChatGPT, Claude, Grok, and Grokbot. Neither timing is a claim about pure provider inference latency. A route resolves before its first action and never switches provider during the run.

Use Begin Provider Check and Record Provider Check to collect the first five responses supplied through the external-provider flow. Use Apply Oracle Recommendation only after the device shows a qualified result. These native App Shortcuts register with the installed app. A personal Shortcut still requires the user to review it and confirm Apple's Add Shortcut and permission screens. Each external provider keeps its authentication and subscription inside its own app. Local Sandbox can validate only the response supplied by the user or returned through Shortcuts against its local challenge and assertions. It cannot prove the response's app or provider origin, inspect the personal Shortcut's contents, or determine whether the provider is signed in. Release acceptance therefore requires live visual evidence of the provider app, selected action, Shortcut contents, and returned result on the physical device. iOS does not expose another provider app's live model activity.

## Autosave and encrypted device sync

The dashboard, hosted `/local` app, and native editor journal drafts before a 650 ms autosave. They serialize writes, verify uncertain results, recover after interruption, and stop for conflicts. The dashboard encrypts its journal in IndexedDB with a device-local key. The local app derives journal encryption from the vault password. Native journals use the selected workspace's file protection and are not separately encrypted at the application layer.

Encrypted device sync is manual and foreground-only. Clients encrypt eligible `workspace/` and `output/` paths and contents before upload. Reserved credential, profile, private-export, and signing-material path segments; `.env` files; and `.cer`, `.key`, `.mobileprovision`, `.p12`, `.p8`, and `.pem` files are rejected even below those roots. The server stores authenticated envelopes and recovery data, not plaintext or workspace keys. Full reads use stable snapshot pages of at most four records and 512 KiB. Clients accept at most 250 pages and 1,000 records, and restart once if a mutation changes the snapshot. Files retain the 64 KB UTF-8 limit. A recovery rotation locally rewraps the same 256-bit workspace key, then replaces the recovery envelope with a snapshot compare-and-swap update and readback. It does not re-encrypt record ciphertext or claim a new data-key epoch. Workspace deletion uses the same snapshot guard and atomically removes that workspace's recovery envelope and ciphertext records. Local Files and iCloud documents are outside that deletion. Nothing polls or syncs in the background.

The server assigns a random 256-bit incarnation to each workspace enrollment. It keeps a bounded epoch history after hosted ciphertext deletion, so the same workspace and epoch cannot return as a new enrollment. Every active workspace must match its exact history tuple. Workspace revisions, record revisions, and hosted file versions stop at JavaScript's maximum safe integer without mutating data. Hosted file versions use one owner-wide monotonic clock, so deleting and recreating the same path never reuses an earlier version.

## GitHub and worktrees

Settings → GitHub authentication & sync accepts a repository-scoped fine-grained token with Contents write, which includes read. The dashboard, local web app, and native app reject classic PAT, OAuth, and GitHub App token prefixes in this manual token field before sending a GitHub request. That format check identifies the credential type; GitHub still decides whether the token can access the selected repository when the app compares or publishes. The dashboard and native creation links prefill a 30-day token with only Contents write, while repository selection remains explicit on GitHub. Dashboard credentials stay in the current tab, and the server proxies requests to GitHub. The dashboard checks remote status every 30 seconds only while the GitHub page is visible. The local app calls GitHub directly, keeps its token in page memory, and performs no polling. Native credentials use the device's Keychain. Every client compares before import or a non-force commit, and branch movement blocks publishing.

The hosted `/local` app can also connect a server-backed Cursor Origin App. It lists permitted repositories and requests an explicit mirror refresh with `repository:contents:read`. Installation credentials never enter the browser, and Origin is not an app login. The generated static self-host package supports direct GitHub access but disables Cursor Origin and encrypted server sync because it has no identity or API server.

To apply an exported worktree patch on a computer:

```bash
python3 scripts/worktree-sync.py Local-Sandbox-Worktree.patch.json --worktree /absolute/path/to/worktree
python3 scripts/worktree-sync.py Local-Sandbox-Worktree.patch.json --worktree /absolute/path/to/worktree --apply
```

The bridge verifies the exact repository, branch, base commit, safe paths, and file hashes. It does not commit, push, or create a worktree automatically.

## Development and updates

Use pnpm and the existing lockfile. Run `pnpm verify` only from the canonical repository checkout. That command requires the private qualification workbook and snapshot plus the committed source ZIP, static self-host ZIP, and setup-guide PDF. Verification is read-only for those committed artifacts and fails when any artifact is stale. Deliberately rebuild the artifacts with `scripts/release/regenerate.py` under Python 3.12 with Pillow 12.3.0, ReportLab 4.4.9, and pypdf 6.10.0, then rerun verification. Set `LOCAL_SANDBOX_RELEASE_PYTHON` when those pinned packages are installed in a non-default Python. On macOS the verifier also parses all Swift sources and runs the portable native contract suites. The public source ZIP omits the private qualification bundle, `docs/validation.json`, committed release downloads, and the canonical repository's `.github` workflows. Those workflows require evidence that the public archive deliberately omits and are available only in the canonical repository. In an extracted source ZIP, run `pnpm run install:ci`, `pnpm run lint`, `pnpm exec tsc --noEmit`, and `pnpm run build` as development checks. Those checks do not create canonical release evidence. The canonical repository's `.github/workflows/verify.yml` contains the full Xcode simulator job. `public/updates.json` is the versioned release manifest. The canonical verifier writes `docs/validation.json` from the checks that it ran.
