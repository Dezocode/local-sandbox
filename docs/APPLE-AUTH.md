# Configure Sign in with Apple

Local Sandbox 0.3 includes first-class web and native Sign in with Apple at `/api/auth/apple/*`. A person can open a standalone Apple-owned workspace or deliberately link Apple to the current ChatGPT-owned workspace. The app never matches or merges accounts by email.

The hosting provider may apply its own access gate before a request reaches Local Sandbox. App-level Apple authentication cannot bypass that external gate.

Do not mark Apple authentication as qualified until the applicable live web and native checks at the end of this guide pass.

## Register the Apple identifiers

1. Enable Sign in with Apple on the primary iOS App ID.
2. Create a Services ID for the web client.
3. Associate the Services ID with the primary App ID.
4. Register the production domain.
5. Register this exact HTTPS return URL:

   ```text
   https://YOUR_DOMAIN/api/auth/apple/callback
   ```

6. Create a Sign in with Apple private key for the primary App ID.
7. Record the Team ID, Key ID, Services ID, and downloaded `.p8` value.

Apple does not accept `localhost`, an IP address, a fragment, or an HTTP return URL. The server rejects those values too.

## Set the server secrets

Set these values in the host's encrypted secret store:

| Name | Value |
| --- | --- |
| `APPLE_AUTH_TEAM_ID` | The 10-character Apple Developer Team ID |
| `APPLE_AUTH_KEY_ID` | The 10-character Sign in with Apple Key ID |
| `APPLE_AUTH_CLIENT_ID` | The Services ID used by the web flow |
| `APPLE_AUTH_NATIVE_CLIENT_ID` | The native iOS bundle identifier used as the native identity-token audience |
| `APPLE_AUTH_REDIRECT_URI` | The exact registered HTTPS return URL |
| `APPLE_AUTH_PRIVATE_KEY_P8` | The complete PKCS#8 `.p8` value, including its header and footer |
| `APPLE_AUTH_STORAGE_KEY` | A base64url-encoded random 32-byte key |

Generate `APPLE_AUTH_STORAGE_KEY` once. Keep it while any Apple sessions remain in D1. Rotating or losing this key invalidates all stored Apple credentials.

```sh
openssl rand -base64 32 | tr '+/' '-_' | tr -d '='
```

Never place the `.p8` value or `APPLE_AUTH_STORAGE_KEY` in source control, the progress workbook, a log, or a client-side environment variable.

## Apply the D1 migrations

Apply every migration through `drizzle/0014_native_apple_session_activation.sql` in filename order with the deployment's normal migration process. The auth tables are:

- `apple_auth_flows` stores one-time state, nonce, browser binding, explicit flow purpose, and the requested owner for a link flow.
- `apple_auth_sessions` stores hashed session identifiers, the resolved opaque workspace owner, a keyed owner binding, and AES-GCM-encrypted Apple credentials.
- `apple_identity_links` maps a keyed Apple subject hash to one opaque workspace owner and a durable Apple principal. Old and new aliases from one server-verified Apple transfer share the principal; unrelated Apple identities do not.
- `apple_native_sessions` stores only hashed 15-minute native bearer identifiers, keyed owner, principal, and subject bindings, and the `pending` or `active` activation state.
- `apple_native_grants` stores the native authorization-code hash, session binding, owner/principal/subject bindings, and the Apple refresh grant as AES-GCM ciphertext. Its associated data binds immutable grant, session, owner, and subject fields; verified alias merges update the relational principal scope in the same D1 batch without rewriting or weakening the ciphertext.
- `apple_native_authorization_code_claims` reserves hashed native authorization codes before the Apple token request so concurrent or retried exchanges cannot send one code to Apple twice.
- `apple_auth_notifications` keeps only keyed notification and subject identifiers, event metadata, a bounded replay receipt, and any bounded Cursor Origin cleanup outcome. It never stores Apple's raw `jti` or `sub`, credentials, profile data, or workspace content. The opaque owner is retained only while destructive cleanup is unfinished and is erased in the fenced completion batch.
- `apple_account_deletions` keeps a keyed idempotency receipt for 30 days. It records the opaque owner and keyed Apple subject, the deletion scope, and the exact revocation summary. It contains no session token or plaintext Apple subject.
- `apple_account_deletion_subjects` durably records every keyed alias in a linked Apple principal before identity links are removed. Owner-operation fences use this bounded membership to deny stale alias operations throughout deletion while still allowing a later, independently authorized generation after completion.
- `apple_owner_external_operation_leases` holds short-lived, opaque authority for one owner-scoped external operation. The row identifies only a bounded provider kind and opaque resource hash; GitHub tokens, repository names, paths, content, and Origin credentials are never stored in it. Linked deletion checks the lease's current principal; standalone deletion checks every lease for that owner. Expired leases do not authorize completion or keep deletion blocked and are removed by bounded request and scheduled cleanup.
- `apple_auth_possible_credentials` keeps at most one conservative, credential-free Apple exchange marker per owner and principal. `prepared` means the provider boundary has not been crossed; `possible` means Apple may have issued a refresh credential that has not been durably stored or confirmed revoked. A possible marker is never aged out or overwritten, and account deletion consumes it into a durable manual-revocation result. Its separate review token rotates before every later provider exchange and every verified principal merge, so an older browser or device cannot acknowledge debt that changed after review.
- `origin_possible_installations` keeps at most one credential-free possible-installation marker for each host owner or Apple principal. It closes the installation callback/deletion race without assuming that a re-consent receipt created a new installation ID. A successful exact-flow save consumes only its own marker; an uncertain callback leaves manual cleanup debt and blocks another install flow in that scope until the person reviews Cursor Origin settings and acknowledges the exact current marker. Principal merges rotate the acknowledgement token before folding debts together.
- `origin_installation_receipt_fences` keeps one signed-receipt issue-time high-water per Origin installation ID. It prevents a delayed or repeated callback from restoring local state after disconnect or after a newer re-consent.
- `apple_auth_admission_cutover` stores the server-created 0013 authorization boundary. Flows, sessions, and grants must be created strictly after that time.

Migration 0006 invalidates only in-flight pre-release v1 web flows. It adds explicit purpose and owner fields, maps each existing v1 session to its owner through `apple_identity_links`, and removes only sessions that have no such mapping. Identity links and workspace data are not changed. A mapped v1 session remains readable: the server first authenticates its v1 ciphertext with the v1 schema and associated data, then re-encrypts it and records schema v2 on the first successful read. It never relabels v1 ciphertext as v2.

Migration 0007 adds the replay and deletion receipts, indexed deletion-gate lookups, and monotonic email-forwarding state. A notification receipt expires after 90 days. A deletion tombstone expires after 30 days; its opaque `owner_id` is required so D1 mutations and session reads can enforce the deletion fence without retaining a credential or profile. Event-time guards prevent a delayed or replayed destructive or email event from changing an Apple link, session, or flow created after that signed event.

Migration 0008 adds expiry-first indexes for deletion receipts and notification receipts. Migration 0009 groups verified transfer aliases under a durable principal and adds expiry-first indexes for web flows, web sessions, and native bearer sessions. Migration 0010 adds encrypted native refresh grants, one-use authorization-code claims, and expiry-first indexes for both tables. Migration 0011 retains every deleted transfer alias for the bounded deletion fence. Migration 0012 adds indexed, five-minute Cursor Origin operation leases. Migration 0013 generalizes those rows to provider-kind and opaque-resource leases for Origin, GitHub, Apple token exchange, and Origin installation flows. It migrates live Origin leases without widening their authority, adds the bounded possible-credential and possible-installation markers, and backfills the main subject plus every still-linked alias available for existing owner-wide deletion receipts. It cannot reconstruct a transfer alias already erased from all pre-0013 rows, so it invalidates every pre-cutover authorization ceremony, web session, native session, and grant instead of admitting ambiguous legacy authority. Migration 0014 rebuilds `apple_native_sessions` with a checked `activation_state`. It copies every pre-0014 row as `active`, while a later insert that omits the column receives the `pending` default.

Treat 0013 as a first-release, fail-closed rollout boundary. The verified source baseline at commit `14ca356` contains only migration 0000 and no Apple-auth worker, but source history does not prove a target deployment's live D1 history. Before migration, read the target's migration history and table inventory. Proceed when the target is pristine at 0000 and will receive the complete 0001–0014 chain, when it is already proved complete through 0013 and will next receive 0014, or when it is already proved complete through 0014. If auth tables or any 0001–0012 migration exist without a complete 0013, stop for manual provenance review. Do not silently upgrade that target. The release precondition is that no 0011 or 0012 auth-capable intermediate worker was ever live against the target. Never roll back a target with auth data to a pre-0013 worker. After applying 0014, never run a pre-0014 worker against new native sessions.

Migration 0013 sets `cutover_at` to the D1 server time plus 300 seconds. Apply the full chain through 0014, read the singleton directly from D1, and wait until wall-clock time is strictly greater than it. Only then deploy and read back the first auth-capable, 0014-aware worker and begin web or native auth qualification. Auth start, callback, session reads, and refresh fail closed across this deliberate five-minute drain interval. Existing pre-cutover web and native sessions and grants require reauthentication. An old worker write during the interval has a creation time at or before the future cutover and remains unusable to the new worker. Migration 0014 keeps copied native sessions active for upgrade continuity, but every new omitted-state row defaults to pending and requires the activation route.

The custom Vinext worker preserves the web fetch handler and declares an hourly Cloudflare Cron Trigger at minute 17 UTC. Its D1-only lifecycle purge drains at most 20 batches of 100 expired rows per table, including native authorization-code claims and external-operation leases. Provider-backed native grant revocation has a separate, smaller bound: one batch of 20 sequential requests, each limited to five seconds, plus a 60-second overhead margin, for a 160-second worst case. Its 240-second claim lease exceeds that bound, while the run stays below the 300-second Apple client-secret lifetime and Cloudflare's 900-second Cron wall-time ceiling. Runtime validation rejects larger caller-supplied batch or timeout combinations. The scheduled timestamp is used only as the stable expiry-eligibility cutoff; every revocation claim and Apple client secret uses fresh wall-clock time, so a delayed Cron event cannot start with an expired secret or immediately reclaim an active operation. A grant is deleted only after successful provider revocation. A failure or remaining backlog fails the scheduled run and leaves durable retry state. A server without Apple configuration can still purge ordinary expired rows when no native grant needs provider access; an eligible native grant without the required Apple configuration fails the scheduled run and remains tracked. Web/native traffic and owner-data mutation checks also run bounded supplemental cleanup. The server retains an expired pending or active native bearer row while its grant exists so possession of that exact bearer can still request explicit revocation. Expiry or pending activation cannot authorize sync or refresh.

The built-worker integration test loads the production server modules and assets, applies every migration to an isolated D1, invokes the real scheduled export through an explicit local user-worker route, and verifies that expired deletion, notification, and external-operation lease rows disappear while future rows remain. The explicit route avoids a Miniflare 4 local assets-proxy serialization limitation; it is test-only and is not part of the deployed Worker. This source/local proof does not establish that the hosting control plane registered or fired the Cron Trigger. Production qualification must read back the deployed trigger, observe a scheduled firing, and confirm the same database behavior. Keep that qualification open until this live evidence exists.

Set `APPLE_AUTH_NATIVE_CLIENT_ID` to the bundle identifier configured for Sign in with Apple in the native Xcode target. The first verified native sign-in for an unseen Apple subject creates a distinct Apple-owned workspace; to reuse an existing ChatGPT-owned workspace, link Apple from that signed-in web account before the first native sign-in.

The native `ASAuthorizationAppleIDCredential` must provide an identity token, authorization code, and the raw nonce generated for that request. The iOS client decodes both credential fields as strict UTF-8 and rejects a missing, malformed, or oversized authorization code before changing an existing unrelated profile. The server first verifies the nonce-bound identity token, then atomically reserves the authorization-code hash. It exchanges the code once at Apple's token endpoint with `APPLE_AUTH_NATIVE_CLIENT_ID` as both the native `client_id` and the client-secret subject, without `redirect_uri`. It requires a refresh token and verifies the exchanged identity token's signature, issuer, native audience, time claims, subject, and transfer-subject continuity. A mismatch or server persistence failure attempts to revoke the fresh Apple refresh token and never exposes it.

Successful exchange atomically persists the encrypted, owner-bound, subject-bound, principal-scoped refresh grant and a 15-minute bearer session in `pending` state. It returns an exact schema-v2 response with `activationState: "pending"`. That pending bearer cannot authorize `/api/sync` or `POST /api/auth/apple/native/refresh`, but `POST /api/auth/apple/native/revoke` can still retire it while the server retains its grant.

The iOS client validates the closed pending-response schema, writes the complete response to the non-synchronizable, device-only `appleNativePendingActivation.v1` Keychain journal, and verifies an exact readback. The journal binds the target account-binding hash, the activation purpose, and any transfer-recovery account-binding hash. An ordinary, transfer-recovery, or deletion-reauthorization flow therefore cannot consume another flow's record, even when the target account is the same. Only after that durable readback does the client prepare to send the same bearer to `POST /api/auth/apple/native/activate`. The serialized persistence gate first checked-reads any prior active-bearer evidence. Unreadable or structurally invalid prior evidence fails before the activation request and remains stored. The server atomically changes a still-valid `pending` session to `active` only while its identity, grant, cutover, revocation, and deletion gates remain valid. Repeated activation of the same qualifying session is idempotent. The active response must return the same token, expiry, and account mode. The persistence gate verifies the journal again, stages any distinct prior revocable bearer before replacement, saves the active bearer, and checks removal of the pending journal. Only that completed active session can enter hosted sync or refresh.

When the app becomes active after a restart, it can automatically resume only a journal whose purpose is `ordinary`. Apple must first report the credential as authorized. The person must then unlock the local profile, and the checked stored Apple user must exactly match the authorized user. Hosted admission remains blocked while the app resumes activation and makes a fresh server refresh, even when the stored bearer expiry is outside the ordinary refresh threshold. The app opens admission only after that refresh and another lifecycle-generation check. Transfer-recovery and deletion-reauthorization journals require their explicit user-driven flows and cannot enter this ordinary resume path.

If the client cannot save and reread the pending journal, it first tries to stage the exact pending bearer in the device revocation queue and then tries remote revocation. If both safeguards fail, the client returns `APPLE_NATIVE_PENDING_SESSION_RECOVERY_LIMITED` and never admits the bearer. The server session remains `pending`, so it cannot authorize sync or refresh. The server's grant-retention path owns cleanup. Before authoritative account deletion completes, invalid pending-journal bytes remain in Keychain and block sign-in and hosted admission. Invalid revocation-queue bytes also remain stored and block bearer admission; neither record is treated as an empty store.

The client samples response time after transport returns for exchange, activation, and refresh. It retains the server's exact expiry only when the response is live at receipt and its expiry is no more than the 15-minute bearer lifetime plus 30 seconds of server-ahead clock skew. Request latency therefore reduces the remaining lifetime instead of becoming extra authority.

While an active bearer remains valid, `POST /api/auth/apple/native/refresh` uses the server-held grant to obtain and verify a fresh Apple identity token. It then extends both rows with a deletion-gated and identity-gated compare-and-swap. A concurrent unlink, transfer-group deletion, account deletion, or session retirement wins by making that update fail. If a grant-row update wins but the session compare-and-swap misses, the encrypted grant remains revocation-pending rather than being deleted. The next scheduler timestamp revokes it with Apple before local deletion, including when a fresh but revoked session row remains. The server returns the same opaque bearer on refresh. The client serializes persistence and keeps the greater valid expiry when same-token responses arrive out of order. A response that races background invalidation may update only that same token's monotonic expiry metadata; hosted admission and in-memory authority stay blocked. A later explicit Lock, deletion, or disconnect captures the greater expiry for retirement. The current implementation requires Apple reauthorization after the Local Sandbox bearer expires. The exact expired bearer remains useful for explicit revocation while the server retains its grant. Apple refresh tokens never appear in a native response or device storage.

Explicit **Lock now** blocks hosted admission before one persistence-gate transaction captures both pending and active sessions. That transaction batch-stages every still-revocable exact bearer, verifies the full queue readback, and only then clears matching active and pending records with checked readback. Transfer handling, disconnect, sync rejection, deletion-recovery discard, and local-profile deletion use the same authority handoff. A checked read or stage failure leaves the original evidence stored and blocked. A later local scrub therefore cannot destroy the last retirement copy. Profile deletion proves the non-identity credential scrub before it clears the Apple user identity as the final commit.

A background transition or bearer expiry ends in-memory and admission authority but keeps exact pending and active Keychain evidence available for retirement. The app proactively retries saved revocations before it sends a new Apple authorization code to `/exchange` and after it promotes an active session. The Settings control runs the same retry manually. Server-confirmed revocation or an authoritative HTTP 401 from `POST /api/auth/apple/native/revoke` removes only the matching debt and matching session evidence; unrelated queue entries remain. The queue's `expiresAt` is a conservative horizon for the possible server grant. Device wall-clock time never clears a queue entry or makes its bearer admissible. Before authoritative account deletion, malformed queue or journal bytes also remain stored and block admission. After authoritative account deletion, checked cleanup may clear the matching active bearer and pending-activation journal because the server has already removed that account's authority. Existing queue debt still requires server-confirmed revocation or an authoritative HTTP 401.

The callback consumes a flow with one atomic D1 delete. A replay, expired flow, wrong browser cookie, or changed ChatGPT owner fails before a session is created. A previously unseen standalone Apple subject receives a random opaque owner ID. Repeated web or native sign-in for that subject reuses the stored owner. A subject already mapped to another owner cannot be linked or merged.

An ambiguous Apple token exchange or failed compensation remains visible after a later successful sign-in. Authenticated web and native Apple sessions read the exact principal-scoped state with `GET /api/auth/apple/possible-credential`. The response contains only `manualReviewRequired`, a server detection time, and an opaque acknowledgement token; the UI never displays the token. After reviewing or removing Local Sandbox under Sign in with Apple in Apple Account settings, the person submits that exact token to `POST /api/auth/apple/possible-credential`. Both clients clear the warning only after strict `{ "acknowledged": true }` confirmation and a final state read. Every intervening auth attempt or verified principal merge rotates the review token, so a stale confirmation receives `APPLE_AUTH_CREDENTIAL_REVIEW_CHANGED` and cannot erase newer or merged debt. A later successful sign-in never silently clears an older possible credential.

For an app transfer, Apple's signed identity token may include `transfer_sub` for up to 60 days. Local Sandbox authenticates that claim in both callback tokens, rejects a mismatch, and uses a previously imported keyed transfer identifier to preserve the existing opaque owner and principal. Generate and exchange transfer identifiers through Apple's documented `userMigrationInfo` process. Apple does not define a transfer server-notification event, so the notification endpoint does not invent one.

When `ASAuthorizationAppleIDProvider` reports `.transferred`, iOS does not treat the credential as authorized or revoked. It immediately blocks hosted-sync admission and saves the durable transfer block. The app then captures both pending-activation and active session evidence and stages each still-revocable bearer before any matching Keychain record can be cleared. If a checked read or stage fails, the exact evidence remains stored and hosted access stays blocked. A staged follow-up records a conservative 30-day native-grant horizon rather than the 15-minute bearer expiry. Validated legacy follow-up records upgrade in place from their bearer deadline to that horizon, but neither version is removed because the device clock passes `expiresAt`. A still-valid pending bearer can request explicit revocation. Server retention makes a grant eligible for scheduled provider revocation after its session expires, its session is revoked, or the grant enters revocation-pending state.

The app also retains the old Apple user identifier needed for recovery. Recovery requires a user gesture on the Sign in with Apple button. That request sets `ASAuthorizationAppleIDRequest.user` to the stored old identifier and retains nonce, state, identity-token, and authorization-code validation. The pending-activation journal binds this transfer purpose and the transfer-recovery account-binding hash, so the same target account under an ordinary sign-in cannot reuse it. The server passes the old identity's required owner and principal into the atomic alias resolver, so a rejected continuity constraint cannot commit a principal merge. Only after the server verifies old and new claim continuity does the app migrate the recovery registry, owner-bound local-workspace directory binding, account-mode binding, and Apple user identifier under a durable journal. The stable directory binding preserves the internal workspace and receipt workspace ID across restart; a selected-folder bookmark, policy, provider qualification, and self-host configuration remain attached to the same local principal. Another device may accept an already-migrated new-user recovery registry only when no stale old-user entry coexists. The journal records whether that device performed the recovery-binding move, so rollback never reverses new-user metadata that already converged from another device. Any failed or unverified migration leaves or restores the durable transfer block. An arbitrary new Apple subject is an account switch and cannot inherit that profile.

## Register and process server notifications

Register this absolute HTTPS URL on the primary App ID in Certificates, Identifiers & Profiles:

```text
https://YOUR_DOMAIN/api/auth/apple/notifications
```

The endpoint accepts Apple's strict JSON `{ "payload": "<JWT>" }` envelope. It verifies the RS256 signature against Apple's current public keys, exact issuer, configured web or native audience, issue time, optional expiry, event time, and keyed `jti` replay receipt before changing data. The supported Apple event types are:

- `email-enabled` and `email-disabled`: update only their own monotonic forwarding-state clock. Email activity cannot suppress a later valid destructive notification, and destructive activity cannot make an older email state current. Local Sandbox does not send email today.
- `consent-revoked` and `account-deleted`: first establish the same durable principal-scoped deletion fence used by the explicit endpoint, then invalidate web sessions and native grants for every verified transfer alias in that principal and remove those aliases. For a standalone `apple-owner:v1.*` account, the handler also deletes all owner-scoped workspace, file, receipt, usage, encrypted-sync, and Origin data. Before local completion it attempts at most eight Cursor Origin installation removals concurrently, with a five-second bound per installation. The fenced notification record stores the exact summary and only the validated unresolved installation IDs; replay never repeats a completed provider call. For an Apple principal linked to a ChatGPT-owned workspace, the handler preserves that workspace, its Origin connections, other Apple principals, and other identities.

A valid signed event type added by Apple in the future receives a replay receipt and a success response but cannot change account state until this code adds an explicit handler. Invalid, stale, future-dated, wrongly addressed, replay-conflicting, or badly signed notifications fail closed.

## Delete an account

Send an empty `POST` to `/api/auth/apple/delete` with a cryptographically random `Idempotency-Key` containing exactly 32 canonically encoded random bytes in `v1.<43 base64url characters>` form.

- A browser request uses the secure Apple session cookie and must be same-origin.
- An iOS request uses the short-lived native bearer token and must not include browser cookies.

The server writes a subject-scoped deletion gate before it calls Apple. That first durable batch atomically rechecks the exact alias, owner, and principal mapping that deletion resolved and refuses to start while a matching unexpired Origin or GitHub operation lease exists. If the deletion gate wins first, the provider route rejects before its remote callback. If a provider lease wins first, deletion returns a retryable conflict until the bounded operation releases it or its five-minute lease expires; expiry cannot authorize a stale success response. A second owner/deletion check after successful provider completion prevents a staged response from escaping if deletion starts immediately after lease release. Host-owned access and an unrelated linked Apple principal remain usable during linked-principal deletion. Web and native session creation and identity binding reject an authorization ceremony whose presented subject or verified transfer alias was deleted after the ceremony began, even if the original identity-link rows are gone. Fresh, newly signed authorization started after deletion completion may establish a later generation. Completing deletion persists the complete verified alias set before removing identity links, so no stale alias can resurrect as a new principal. Completing one attempt atomically completes every live retry key for that same owner-and-subject scope with the same summary, so a second device cannot leave a stale sign-in gate behind. If Apple issued a web refresh token before the gate stopped local session creation, the callback attempts to revoke that token.

The server reads at most eight web sessions and eight native grants and revokes their unique refresh tokens in parallel. It also reads at most eight standalone-account Cursor Origin installations and attempts their removal concurrently with a five-second bound. Extra, unreadable, unconfigured, or failed provider records set the corresponding `manualRevocationRequired` flag, but they do not block Apple-required local deletion. The final D1 batch stores both exact summaries and removes the selected Apple principal's access.

For a standalone Apple owner, the batch also deletes the owner's workspace, files, receipts, usage, encrypted sync records, Origin data, native sessions and grants, web sessions, identity links, and pending Apple flows. For a linked Apple principal, the batch deletes sessions, grants, and identity links for every verified transfer alias in that principal. The ChatGPT-owned workspace, unrelated Apple principals, other linked identities, and unrelated pending flows remain.

The web client stores the random key with the opaque owner-and-subject deletion scope and the exact workspace scope before it sends the request. A reload can replay the same key without a session cookie and still locate that workspace's local encrypted drafts. After strict server confirmation, the client synchronously invalidates its workspace generation and immediately publishes a scoped cross-tab lock. It then drains queued autosave journal writes, deletes and verifies only that workspace's IndexedDB draft records, clears its in-memory device-key reference, and only after that verified cleanup clears the retry attempt and publishes completion. Drafts for other workspace scopes and their shared persistent encryption key remain intact. Every receiving tab performs the same generation invalidation and targeted cleanup, so a delayed sync, plan, check, import, or connector request cannot restore deleted-account state, a GitHub token, a workspace key, or plaintext.

The iOS client stores the key and original bearer as one globally discoverable Keychain transaction before the request. Schema v3 also stores the exact bearer expiry, so a later discard can derive the conservative grant horizon from the bearer the server actually returned. Legacy schema v2 did not store that expiry. Discard therefore treats legacy timing as ambiguous and retains retirement debt through the attempt deadline plus 30 days and 30 seconds. The fallback exists only for retirement; the app never presents it as the bearer's issuance or response time.

If the original bearer expires before the server receives the request, a fresh user-authorized Sign in with Apple ceremony can reauthenticate the same Apple identity without changing the deletion key. The deletion reauthentication purpose is part of the pending-activation journal binding, so an ordinary sign-in cannot consume that activation. A process-wide UI flag spans Apple request preparation through sign-in completion. It disables a second Apple ceremony and conflicting Lock, profile deletion, deletion-recovery discard, and revocation-retry controls during that interval. A lock, app restart, or lost response cannot change the logical deletion attempt. Background lock synchronously advances the bearer-persistence gate and the UI lifecycle generation, removes in-memory and hosted-admission authority, and clears in-memory sync state. It retains the exact normal bearer and pending-activation Keychain evidence for checked retirement or deletion recovery. The gate serializes its generation check with each Keychain write, so delayed or out-of-order token exchanges, unlocks, pulls, or writes cannot restore hosted authority, a workspace key, or plaintext after lock. The app observes Apple's credential-revoked notification and rechecks credential state whenever it becomes active, while preserving any uncertain deletion transaction for recovery. After authoritative server deletion, the client may checked-clear matching local session evidence because the server has removed that account's authority.

After strict server confirmation, iOS persists the result before checked local cleanup. Cleanup removes the bearer, provider credentials, persisted account mode, and every synchronizable hosted-workspace recovery secret registered to that Apple profile. It verifies those non-identity removals while the stored Apple user still identifies the profile, then clears that identity as the final commit. Cleanup also clears in-memory workspace state and disconnects folder access, but it never deletes user-selected Files or iCloud documents. A Keychain failure leaves the completion transaction available for retry. Manual Apple Account removal guidance remains durable until the person dismisses it.

A retry with the same key returns the original revocation summary. A valid session from another owner or Apple subject receives a conflict. Without a valid session, the random 256-bit key acts only as a capability to resume its pending attempt or read its completed receipt.

Apple requires account deletion to finish even when no provider token exists or token revocation fails. In that case the response sets `providerCredentials.manualRevocationRequired` to `true`; the client must direct the person to remove the app under their Apple Account's Sign in with Apple settings. The server never retains a token after local deletion just to retry revocation.

## Qualify the live flow

Run all checks on the registered production HTTPS domain:

1. Sign out of ChatGPT, open the Local Sandbox sign-in screen, and choose **Continue with Apple**. The client sends a same-origin JSON `POST` to `/api/auth/apple/start` with `purpose: "authenticate"`.
2. Complete Apple authentication and confirm that the Apple-only session can request `/api/workspace` without ChatGPT identity headers.
3. Confirm that Apple posts to `/api/auth/apple/callback` with `form_post`.
4. Confirm that the callback returns to `/?apple_auth=connected`.
5. Request `/api/auth/apple/session`. Confirm that it returns `authenticated: true`, `mode: "standalone"`, the opaque workspace owner, and no Apple token.
6. Sign in through ChatGPT, open Account, and choose **Link Apple to this workspace**. Confirm that the start request uses `purpose: "link"` and the Apple session resolves to the same workspace owner.
7. Repeat the callback POST. Confirm that the server rejects the used state.
8. Start a second flow in another browser. Confirm that swapping either flow cookie causes a binding error.
9. Attempt to link an Apple subject that already owns a different workspace. Confirm that the server returns HTTP 409 and does not merge either workspace.
10. Submit a same-origin POST to `/api/auth/apple/revoke`. Confirm that Apple receives the refresh-token revocation request and the next session read returns `authenticated: false`. The server invalidates the local session even if Apple's revoke endpoint is temporarily unavailable.
11. Inspect D1. Confirm that plaintext session cookies, native authorization codes, Apple subjects, email addresses, access tokens, and refresh tokens do not appear in the auth tables. Opaque Local Sandbox owner IDs are expected in `owner_id`.
12. Register the notification URL and exercise all four Apple event types. Confirm duplicate JWTs are idempotent, older relay events cannot roll state back, and a notification for a linked ChatGPT workspace removes only Apple access.
