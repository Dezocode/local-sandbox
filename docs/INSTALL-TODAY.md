# Local Sandbox 0.3: installation paths

This release includes a working web implementation and native source with portable Swift contract coverage. It is not a signed or App Store-qualified native build. No signed provider Shortcut installers are bundled.

## On-device web workspace

Open `/local/index.html` from the hosted Site. Create a vault password of at least 12 characters. In Safari, use Share → Add to Home Screen and enable Open as Web App where offered. The page registers an offline shell. Installation, lifecycle, storage persistence, and offline behavior still need testing on the target iPhone. The encrypted local vault is separate from the dashboard's D1 workspace.

Files and manually transferred Oracle/Locally messages are encrypted with AES-GCM before IndexedDB storage. PBKDF2 derives the key from your vault password with a fresh salt and 600,000 iterations. The password stays in page memory until Lock or page closure. Export encrypted backups. Clearing website data or losing the password can lose access. A second tab cannot overwrite a newer vault revision silently. This is password protection, not an Apple passkey or Face ID implementation.

The local editor journals each encrypted draft before a 650 ms autosave. It serializes vault writes, detects changes from another tab, keeps failed drafts for retry, and restores an interrupted draft for review. Save now flushes pending work before an export. Nothing saves or syncs in the background after the browser suspends the page.

The hosted `/local` deployment also exposes manual encrypted workspace sync and Cursor Origin controls through the hosted identity and API service. Direct GitHub access stays in the browser. For an independent static deployment, run `python3 scripts/release/selfhost.py` and host `public/downloads/Local-Sandbox-Selfhost.zip`. Do not copy the raw `public/local` folder, whose capability manifest describes the hosted deployment. The generated static package retains direct GitHub access but disables Cursor Origin and encrypted server sync. Changing origins does not move browser storage. Export and restore an encrypted backup with the same password.

Before enabling hosted Apple sign-in, qualify the target D1 as the first 0.3 auth rollout described in `APPLE-AUTH.md`. Accept a pristine 0000 database only when it receives the complete 0001–0014 chain. You may also apply 0014 to a target already proved complete through 0013, or use a target already proved complete through 0014. Auth tables or partial auth migrations without a complete 0013 require manual review. Do not deploy or roll back to an auth-capable 0011 or 0012 worker. Apply through 0014, read `apple_auth_admission_cutover` directly from D1, and wait until wall-clock time is strictly greater than `cutover_at`. Only then deploy and read back the first auth-capable, 0014-aware worker and start sign-in tests. Migration 0014 copies existing native-session rows as `active`; a later insert that omits `activation_state` defaults to `pending`. The five-minute future cutover from migration 0013 invalidates old auth ceremonies, sessions, and grants and requires reauthentication.

## Native Xcode source

1. Unzip the source. Open `ios/LocalSandbox.xcodeproj` in Xcode with an SDK that supports the connected phone and the iOS 26 deployment target.
2. Select your Apple Developer team and a unique bundle ID. Configure Sign in with Apple for that App ID. To use the hosted exchange, set the same bundle ID as `APPLE_AUTH_NATIVE_CLIENT_ID` on the server. The entitlement requires valid provisioning. A source ZIP does not supply it.
3. Build to your connected, trusted iPhone. On the release Mac, Xcode 27 has completed a generic iOS Release build and a generic iOS Simulator build-for-testing without warnings. The iOS 27.0 simulator runtime is installed, the exact project-owned test command passes 32/32 tests on the selected iPhone 18 Pro Max simulator, and the app launches standalone to its Sign in with Apple screen. Those simulator results do not configure development signing, install or launch the app on a physical iPhone, or satisfy any live-device gate. Resolve entitlement and provisioning errors before distribution.
4. If this phone must reopen an existing ChatGPT-owned workspace, sign in to that web account and link Apple before the first native sign-in. A first native sign-in for an unseen Apple subject creates a separate Apple-owned workspace. Local Sandbox never merges owners by email.
5. Sign in with Apple. The app binds a raw nonce to the Apple request and exchanges the returned identity token and one-use authorization code. The server returns a schema-v2 `pending` response with a 15-minute bearer. The iPhone writes that exact response to the device-only `appleNativePendingActivation.v1` Keychain journal and verifies the readback before it calls `POST /api/auth/apple/native/activate`. The journal binds the target account-binding hash, activation purpose, and optional transfer-recovery account-binding hash, so ordinary, transfer-recovery, and deletion-reauthorization records are not interchangeable. The app checked-reads any prior active-bearer evidence and fails before activation if that evidence is unreadable or structurally invalid. The app admits only the same session returned as `active`; pending sessions cannot authorize encrypted sync or refresh. After a restart, the app resumes only an ordinary pending record. It keeps admission blocked while Apple reports the exact stored user as authorized, you unlock the profile, activation finishes, and a fresh server refresh succeeds. Transfer recovery and deletion reauthorization require their explicit flows. The client validates each exact server expiry at response receipt with at most 30 seconds of server-ahead clock skew. Concurrent valid refreshes for the same bearer preserve the later expiry without replacing the token. While this Apple ceremony is active, the native UI disables a second ceremony and conflicting profile, lock, deletion-recovery, and retry controls.
6. Unlock through Face ID or the device passcode. Explicit **Lock now** blocks hosted admission, then performs one serialized capture, batch stage, and checked handoff for every pending or active session that may still have a server grant. It clears matching session evidence only after the full queue write succeeds and reads back. A background transition or bearer expiry ends in-memory and admission authority but retains the exact Keychain evidence needed for later retirement. Transfer handling and local-profile deletion use the same stage-before-clear rule. Profile cleanup verifies every non-identity deletion before it clears the Apple user identity as the final commit. Use **Retry native-session revocation** in Settings to retry saved debt; the app also retries before a new Apple exchange and after active-session promotion. A confirmed revoke or authoritative HTTP 401 removes only its matching queue entry. The app preserves unrelated entries. The displayed `expiresAt` is a conservative server-grant horizon, not a device cleanup deadline, and device wall-clock time never clears debt. Before authoritative account deletion completes, invalid pending-activation journal or revocation-queue bytes remain stored and block hosted admission. After authoritative hosted deletion, checked cleanup may clear the matching active bearer and pending-activation journal because the server has removed that account's authority. Existing queue debt still requires confirmed revocation or an authoritative HTTP 401. Native workspace files use complete file protection in Application Support. A selected Files or iCloud folder follows its provider's protection and availability rules.

If a post-exchange client failure prevents both durable staging and remote revocation, the app reports `APPLE_NATIVE_PENDING_SESSION_RECOVERY_LIMITED` and keeps hosted admission closed. That server session remains pending, so it cannot sync or refresh. Server retention owns cleanup. Do not treat source tests as proof that the production Cron Trigger is registered or firing.

Hosted deletion retries use a schema-v3 Keychain attempt that stores the exact bearer expiry. If you discard a legacy schema-v2 attempt, the app preserves a conservative retirement horizon through the attempt deadline plus 30 days and 30 seconds because that schema did not store bearer expiry. This fallback is retirement metadata, not a claim about when Apple or the server issued the bearer.
7. In Encrypted workspace sync, choose either a random 256-bit recovery secret in synchronizable iCloud Keychain or a local-only passphrase. Back up the one-time random secret if a browser must recover the workspace. The recovery lifecycle section can prove and save an existing passphrase to iCloud Keychain, rotate the recovery credential with compare-and-swap readback, remove the synchronizable Keychain item, or delete one hosted encrypted workspace. After refresh, an obsolete-credential section exposes account-scoped Keychain entries left by an interrupted hosted deletion for explicit, device-authenticated cleanup. Rotation keeps the existing workspace data key and ciphertext. Hosted deletion and credential cleanup keep local Files and iCloud documents. A deleted hosted workspace cannot reuse its earlier key epoch because the server retains a bounded enrollment history and assigns each enrollment a random incarnation. Only non-private `workspace/` and `output/` descendants are eligible: reserved credential, profile, private-export, and signing-material paths; `.env` files; and `.cer`, `.key`, `.mobileprovision`, `.p12`, `.p8`, and `.pem` files are rejected. Sync is explicit and foreground-only.
8. Native file edits journal before a 650 ms autosave. The app serializes guarded writes, reads back uncertain results, retains failed drafts, and stops for conflict review. The journal is stored under `state/autosave/` and is not separately encrypted at the application layer.
9. In Local Sandbox, open Settings → Shortcut setup and use the native Shortcuts link to open the app's App Shortcuts page. Installing the native app registers nine actions on iOS 26 and later: Prepare Workspace, Begin Oracle Task, Apply Validated Action, Run Bounded Task, Begin Provider Check, Record Provider Check, Qualify Apple Intelligence, Apply Oracle Recommendation, and Open Local Sandbox. iOS 27 also exposes Run Long Apple Task, which uses the system's long-running App Intent lifecycle for direct Apple Intelligence execution. Run and Begin expose Saved provider, Best local, Apple Intelligence, Locally, ChatGPT, Grok, Grokbot, and Claude. Every action except data-free Open Local Sandbox requires local-device authentication on the executing iPhone before protected state is read or changed. This registration does not install a personal or third-party provider Shortcut. Native registration has not been tested on a device here.

## Fix `Agent Step - Local does not exist`

`shortcuts://run-shortcut` can only run an already-saved Shortcut. `shortcuts://create-shortcut` opens an empty editor. Neither creates the requested provider workflow automatically.

Create a Shortcut named **Agent Step - Local**. Pass Shortcut Input to the text-generating action offered by your installed Locally app. Finish with Stop and Output. If Locally offers no such action, use the manual transfer path and return its response yourself. Do not invent a Locally, LM Link, Grokbot, or other vendor action identifier.

Save the workflow, confirm the exact name in Settings, and run the read-only text test. Visually confirm on the phone that the intended provider app and action ran and that its result returned through the reviewed Shortcut before you mark the test passed. The app records your device report, but it cannot inspect your Shortcut inventory or attest which app produced returned text. The same process applies to ChatGPT, Grok, and Claude, using their own app accounts and exposed actions. Cloud handoff consent must also be enabled for cloud providers.

To provide a direct handoff to Apple's Add Shortcut screen, export the tested Shortcut through Apple's sharing flow. Choose Anyone where appropriate, or copy its iCloud share link. Put that real link in the provider settings. This source does not bundle fabricated installer links. The user must review and confirm Apple's Add Shortcut and permission screens.

## Qualify a provider deterministically

Use the same five probes for each provider: `strict-json`, `read-tool`, `list-tool`, `patch-tool`, and `bounded-context`. The protected ledger stores at most 240 attempts. It admits at most one attempt for each provider, probe, and UTC day. Complete the first five distinct probes within seven days on the same device, full OS major, minor, and patch version, OS build descriptor, app version and build, and adapter name and mode. Qualification scores use only the 20 freshest attempts in the seven-day window. A change to any epoch value starts a new qualification suite.

For Locally, ChatGPT, Grok, Grokbot, or Claude, create or install the personal provider Shortcut and confirm Apple's prompts. Then repeat this flow until all five probe names have results:

1. Run Begin Provider Check and choose the exact provider.
2. Use Get Dictionary from Input on the returned challenge.
3. Send only its `payload` to the exact configured provider action.
4. Pass the challenge's provider, attempt ID, and raw returned response to Record Provider Check.

Run Apple's five checks from Apps & Shortcuts. A provider qualifies only with all five completed probe types, a local schema-validation pass rate of at least 80%, an exact-assertion pass rate of at least 80%, and zero integrity faults. The first suite therefore needs at least four schema-valid responses and four passing assertions. Every task route, including direct Apple Intelligence, requires that full base qualification plus all three tool probes and enough tested context for that task. An external Siri route also requires an observed App Intent return for every probe. The observation records only that returned text reached Record Provider Check. It does not prove unattended end-to-end execution, the response source, the provider account, or the active model. A manual-return route is never eligible for unattended Siri. Provider authentication stays in the provider app. Record live visual evidence of the provider app, action, reviewed Shortcut, and returned result on the physical device before accepting unattended operation.

After the required providers qualify, run Apply Oracle Recommendation. The app ranks eligible providers by schema-validation rate and assertion pass rate. Equal external-provider scores then use lower observed App Intent round-trip time in 500 ms buckets. Apple records in-process model time, which is not compared with an external round trip. Remaining ties use the fixed order Apple Intelligence, Locally, ChatGPT, Claude, Grok, and Grokbot. Neither timing is pure provider inference latency. Saved and explicit selections never substitute. Best local considers only Apple Intelligence and Locally. Its cold start applies only while neither has comparable evidence: it targets available Apple, otherwise Locally, but blocks execution until that route has a current task-qualified suite. As soon as either has comparable evidence, Best local uses the measured rank and blocks if its selected route does not qualify. Every run fixes its route before the first action and never switches provider mid-run.

## Siri and repository connections

Use Siri to invoke Local Sandbox's declared App Shortcuts or let Shortcuts compose them into a larger workflow. Run and Begin return a closed version 1 envelope. First use Get Dictionary from Input. Branch on its `decision`: `on-device-apple` contains a terminal receipt in `payload`, while `app-shortcut` contains the configured `adapterName` and provider prompt in `payload`. For a provider app, send only that `payload` to the user-reviewed provider Shortcut, pass the returned raw JSON text to Apply Validated Action, then decode Apply's returned envelope. Apply enforces the saved authorization and action schema but does not display a separate per-action content review in an unattended flow. Repeat with its next `payload` only while `phase` is `awaiting_response`; otherwise retain or import the terminal receipt from `payload`. Sign in inside the provider app; Local Sandbox never imports or detects its token or login state. On iPhone 18 Pro Max, selecting Apple Intelligence uses the on-device Foundation Model directly. iOS 27's Run Long Apple Task provides extended execution with progress and cancellation; the iOS 26 Run, Begin, and Apply actions remain available for lower-device workflows. Lower devices retain the same native workspace actions and explicit provider selection through Shortcuts.

The app does not replace the default assistant, silently choose another provider, or read private provider chat histories. Provider-app receipts record only the configured provider, requested selection, Local Sandbox origin, action order, a SHA-256 adapter fingerprint, and prompt/response SHA-256 values for the handoff. They do not export the custom adapter name or attest the response source. The native app gates new work with its own qualification, run, pending-response, and applying-response state. Export the terminal receipt from the phone and deliberately import it on the dashboard Activity page to inspect the validated app-owned route and handoff timeline. The dashboard does not receive live native or provider activity. No automatic live receipt sync, provider sign-in detection, model-activity detection, or cross-app telemetry is claimed.

GitHub settings require a `github_pat_` fine-grained personal access token. On GitHub, select only the repository you will sync and grant Contents write, which includes read. The dashboard and native creation links prefill that permission and a 30-day expiry, but you must choose the repository. A successful account check does not prove repository access; compare the selected file to test the actual grant before publishing. The dashboard checks remote status every 30 seconds only while its GitHub page is visible. The local web app performs no polling and calls GitHub directly only after a user action. Publishing uses expected commits and non-force updates. The worktree bridge applies reviewed exported patches to an existing worktree. Private config, state, and logs are excluded from file sync.

The hosted `/local` app can connect a Cursor Origin App installation, list permitted repositories, and request a manual mirror refresh with `repository:contents:read`. The server owns the short-lived installation credential. The browser never receives it. Origin is not a Local Sandbox login, does not write a repository, and performs no background polling. The native app and generated static self-host package do not expose Origin controls.
